Canvid PWA: where the app ends
and the extension begins

MVP implementation snapshot from September 2, 2026. Visual writeup revised September 4.

One app, two installs. The PWA owns the UI and media. The companion runs Chrome APIs the PWA cannot call directly.

1. The boundary that matters

flowchart LR
  subgraph PWA[Hosted PWA]
    UI[React UI and recording logic]
    WEB[Web APIs and OPFS storage]
    CLIENT[Companion message client]
    UI --> WEB
    UI --> CLIENT
  end
  subgraph EXT[Installed companion extension]
    HANDLER[MV3 service worker]
    API[desktopCapture / system / windows]
    HANDLER --> API
  end
  CLIENT -->|sendMessage to known extension ID| HANDLER
  HANDLER -->|Serializable response| CLIENT

The manifest allowlists the PWA origin. Capture and window actions use the sender tab, not an arbitrary window selected by the page. Media processing stays in the PWA.

Before: assumes an extension page

recording.start()
  chrome.windows.getCurrent()
  chrome.windows.update(...)

Fails in a PWA: chrome.windows is absent.

After: route privileged work

recording.start()
  minimizeCurrentChromeWindow()
    PWA → companion message
    companion → sender window
    extension page → direct API

Existing full-extension behavior is retained.

2. Startup is a gate, not discovery

The PWA must already know the extension ID. Loading an extension alone does not tell the page which extension to call.

bootstrap
  load browser shim
  ping(configured extension ID)
    OK
      register PWA service worker
      import normal app entry
    unavailable / rejected
      load current locale
      render I18nProvider
        render extension-required screen

Both sides must agree

PWA configuration
  VITE_COMPANION_EXTENSION_ID
            │
            ▼
Installed companion identity
  stable manifest public key

PWA origin
            │
            ▼
externally_connectable.matches
  allowed hostname and scheme

Local development wires the stable ID and loopback origin automatically. Production must use the actual published extension ID and hosted origin.

3. Recording crosses the boundary only when needed

sequenceDiagram
  participant P as PWA
  participant E as Companion
  participant C as Chrome
  P->>E: choose-desktop-media
  E->>C: chooseDesktopMedia(sources, sender.tab)
  C-->>E: streamId + audio availability
  E-->>P: capture result
  Note over P: Consume stream ID promptly and prepare recording
  P->>E: minimize-current-window
  E->>C: minimize sender.tab.windowId
  E-->>P: result
  Note over P: Schedule recording activation after 500 ms
  loop Existing 500 ms restore watcher
    P->>E: get-current-window
    E->>C: read sender window state
    C-->>P: window state, via companion
  end
  Note over P: When recording and restored: stop recording

Other bridged reads: system-display, system-cpu, and system-memory. The bridge is not a blanket exposure of every Chrome API.

4. Development produces two artifacts

pnpm dev:pwa
├── build:companion-ext:dev
│   └── dist-companion   → load unpacked in Chrome/Helium
│       origin allowlist: http://127.0.0.1/*
└── Vite browser server → open 127.0.0.1:5173
    stable companion ID supplied automatically

Production
├── pnpm build:pwa           → dist-pwa       → HTTPS hosting
└── pnpm build:companion-ext → dist-companion → extension distribution

Commands run from the desktop package. After companion code changes: rebuild and reload the unpacked extension. After environment changes: restart Vite and reload the PWA. Installing the PWA remains a separate browser action.

Why the first runs failed 
Standalone startup screen
- Trans without a provider
+ load locale → I18nProvider → Trans

Companion connection
- missing ID; hosted-origin allowlist only
+ stable dev ID; loopback allowlist

Runtime version
- runtime?.getManifest()
+ runtime?.getManifest?.() with web fallback

Recording start and restore polling
- direct chrome.windows calls from PWA
+ shared helpers route through the companion

What is proven, and what is still MVP

Checked during implementation

  • PWA and companion builds completed.
  • Focused messaging and browser-shim tests: 17/17 passed.
  • Missing-method runtime shapes are covered.

These checks do not prove a complete live recording-to-export session. Renderer typechecking also had two unrelated supportsRandomAccess errors.
