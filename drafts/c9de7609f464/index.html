Screenshot Editor: Windows Shape Label Export Investigation

Agent handoff report for reproducing and fixing a preview versus export text mismatch.

Status: needs Windows reproduction Area: screenshot-editor Likely cause: subpixel text metrics macOS: not reproduced
Bottom line: the preview uses browser DOM text while the export uses Pixi HTMLText rendered through SVG. The label has only about 0.508 px of spare wrapping width on macOS. A small Windows font-metric difference can wrap the final word even though the black label box keeps the preview dimensions.

Problem

Shape-label text fits inside its black label box in the editor preview, but can wrap or overflow after exporting the image.

Reproduction

  1. Open the displayed /screenshot-editor URL.
  2. Load the demo screenshot.
  3. Draw a tapered arrow.
  4. Add a shape label at either endpoint.
  5. Enter exactly This is another sample of a text.
  6. Export immediately after editing.
  7. Compare the editor preview with the exported PNG.
  8. Repeat at editor zoom levels around 32%, 76%, and 100%.
  9. Repeat for both the start and end labels.

Expected: the label remains on one line in both preview and export.

Reported Windows result: the exported text wraps while the black box retains its preview dimensions.

Measured evidence

On macOS, the exact label measured:

outer width:   353.4921875 px
outer height:  46 px
font:          24px / 34px sans-serif
maximum width: 480 px

The code rounds the outer width to 354px, then subtracts 20px of horizontal label chrome. The export wrapping width becomes 334px.

334 - 333.4921875 = 0.5078125 px spare

That is a very narrow margin. If Windows or SVG measures the text just over half a pixel wider, the final word wraps. This points to a measurement-boundary bug, not missing letter spacing.

Ranked hypotheses

  1. Most likely: Windows DOM and Pixi SVG/HTMLText metrics differ by more than the available ~0.5px.
  2. Less likely: export captures a stale asynchronous HTMLText texture immediately after editing.
  3. Mostly ruled out: preview and export use different placement geometry. They share one render plan, and the reported box placement looks correct.

The immediate-edit-then-export case worked on macOS. The export code also waits for HTMLText texture promises, which makes the stale-texture theory weaker.

Windows evidence to capture before editing

  • window.devicePixelRatio
  • getBoundingClientRect() for the hidden label measurement element
  • Calculated outer width and content wordWrapWidth
  • Computed font-family, font-size, font-weight, and line-height
  • Whether waiting for document.fonts.ready changes the result
  • Whether waiting one second before export changes the result
  • Whether adding 1px or 2px to only the export wrapping width prevents wrapping
  • The actual default sans-serif font used by DOM and Pixi SVG

Smallest likely fix

If Windows confirms the subpixel-width hypothesis, give exported HTMLText a 1 to 2 source-pixel wrapping tolerance while leaving the black box geometry unchanged.

The label already has 8px of internal padding, so the tolerance can borrow from that padding without visibly enlarging the box.

Keep the change inside buildShapeLabelHtmlStyle. Do not add a second measurement system or refactor the renderer unless the Windows measurements disprove this diagnosis.

Add one focused test that confirms:

  • export text receives the tolerance;
  • preview and box geometry remain unchanged.
