PR #2413 into release-v3

How we resolved a conflict caused by squash-release history, kept main as the definitive codebase, passed the deployment gate, and landed the release as one squash commit.

The short version

release-v3 contained the previous release as a squash commit. main contained the same code through its original commits. The files were logically related, but Git saw different histories and reported conflicts.

Because main was explicitly authoritative, we did not merge file contents from release-v3. We added a no-content merge commit to main using Git's ours merge strategy. That recorded the release branch as merged while keeping the main tree byte-for-byte unchanged.

Result: GitHub could calculate a clean merge, PR #2413 was squash-merged, and the final release-v3 tree exactly matched the PR head.

Why the conflict existed

What Git saw

  • main and release-v3 shared merge base 2e3953aa.
  • main had 215 commits not in release-v3.
  • release-v3 had 2 commits not in main.
  • The previous 3.1.0 release was represented by a new squash commit on release-v3.

What humans knew

  • The previous release code already existed on main.
  • The different commit IDs came from squash merging, not unique release work that needed preservation.
  • For 3.1.1, the complete main tree was the intended release.
  • Any content-level blend with the old release tree would be wrong.

The exact process

  1. Pin the live PR and remote branches

    Confirm the PR really targets release-v3 from main. Record both remote commit IDs before changing anything.

    gh pr view 2413 --json baseRefName,baseRefOid,headRefName,headRefOid,mergeable,mergeStateStatus
git fetch --prune origin main release-v3
git rev-parse origin/main origin/release-v3
    Stop if either branch moves. Re-fetch and redo the comparison. Do not resolve against stale refs.

  2. Prove the conflict is ancestry, not unique release code

    Inspect divergence and the release-only commits. For this PR, the release-only code was the previous squash release, while main was explicitly declared definitive.

    git merge-base origin/main origin/release-v3
git rev-list --left-right --count origin/release-v3...origin/main
git log --oneline origin/main..origin/release-v3
git diff --stat origin/release-v3..origin/main

  3. Create a temporary worktree at the pinned PR head

    This keeps the normal checkout and any unrelated work untouched.

    tmp=$(mktemp -d /tmp/canvid-release.XXXXXX)
git worktree add --detach "$tmp" <pinned-main-sha>

  4. Record release ancestry without taking release contents

    Use the merge strategy -s ours. This deliberately keeps the full current main tree, not just main's side of conflicting hunks.

    git -C "$tmp" merge -s ours --no-ff <pinned-release-sha> \
  -m "chore(release): reconcile release-v3 history" \
  -m "Record the prior squash release as merged while retaining main's tree unchanged."
    Do not replace -s ours with -X ours. -X ours only chooses our side for conflicting hunks and can still pull non-conflicting stale release changes into main.

  5. Prove the reconciliation changed no files

    git -C "$tmp" diff --exit-code <pinned-main-sha>..HEAD
git -C "$tmp" diff --check <pinned-main-sha>..HEAD
git -C "$tmp" rev-parse <pinned-main-sha>^{tree} HEAD^{tree}

    The two tree hashes must be identical. For this run, both were 34d100ac1b01eb17f50bf1a515321835c412884f.

  6. Push with a lease pinned to the inspected head

    git -C "$tmp" push \
  --force-with-lease=refs/heads/main:<pinned-main-sha> \
  origin HEAD:refs/heads/main

    The lease makes the push fail safely if somebody updated main after inspection.

  7. Wait for GitHub and CI to settle

    gh pr view 2413 --json headRefOid,baseRefOid,mergeable,mergeStateStatus,statusCheckRollup

    GitHub briefly reported MERGEABLE / UNSTABLE while Vercel ran. The first Vercel attempt failed because Turborepo restored a cached successful build without a usable dist artifact. A redeploy with the build cache disabled rebuilt the output and passed.

    Cache-specific recovery: only retry without cache when logs show the build itself succeeded but the expected output directory is missing. A real compiler or test failure needs a code fix.

  8. Squash merge, pinned to the verified head

    gh pr merge 2413 --squash --match-head-commit <verified-head-sha>

    Do not pass --delete-branch. The PR head is main.

  9. Prove the final release tree matches the PR

    git fetch origin main release-v3
git diff --exit-code origin/main^{tree} origin/release-v3^{tree}
git rev-parse origin/main^{tree} origin/release-v3^{tree}
gh pr view 2413 --json state,mergedAt,mergeCommit

    The diff must be empty and both tree hashes must match.

Why this solution was the smallest safe one

We did

  • Add one no-content ancestry commit.
  • Keep the authoritative tree unchanged.
  • Use GitHub's normal squash merge.
  • Verify exact tree equality afterward.

We skipped

  • Hand-resolving roughly 190 changed files.
  • Force-resetting the published release branch.
  • Creating a replacement PR.
  • Adding special release tooling for a one-off conflict.

When to use this again

Use this workflow only when all of these are true:

  • The PR head is the complete, authoritative tree.
  • The base branch's unique commits are previous squash-release history, not release-only fixes that must survive.
  • The team explicitly wants the base tree replaced by the PR tree.
  • A merge commit on the PR head is acceptable.
  • The final PR merge will be a squash.
Do not use this for normal feature conflicts. The ours strategy discards the other branch's complete tree. It was correct here only because that was the stated release policy.
